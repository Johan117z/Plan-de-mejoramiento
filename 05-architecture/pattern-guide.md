## Patterns adopted in this project

> Documentación de los patrones de diseño y microservicios adoptados en la arquitectura de **FixGo**, alineados con la estrategia de alta disponibilidad, despacho geoespacial en tiempo real y consistencia eventual.

| Pattern                        | Adopted? | Justification / ADR                                                                                                                                                                                                           |
| ------------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API Gateway**                | Yes      | Centraliza el enrutamiento edge, la terminación TLS, la validación de tokens JWT y la limitación de tasa (rate-limiting) previa a los microservicios core. Ver `ADR-001`.                                                     |
| **Database per Service**       | Yes      | `fixgo-iam-service`, `fixgo-dispatch-service` y `fixgo-workshop-service` manejan sus propios esquemas aislados (PostgreSQL / PostGIS). Evita el acoplamiento directo en base de datos. Ver `ADR-001`.                         |
| **Circuit Breaker**            | Yes      | Protege las integraciones con servicios externos críticos de baja tolerancia a fallos, como la API de Mapbox (rutas/geocodificación) y el Gateway de Pagos. Implementado con Resilience4j / Opossum.                          |
| **Saga (Choreographed)**       | Yes      | Gestiona las transacciones distribuidas en el flujo de solicitud de asistencia vial (Solicitud -> Reserva de Operador -> Pago/Confirmación) mediante eventos asíncronos en RabbitMQ.                                          |
| **Outbox Pattern**             | Yes      | Garantiza la publicación atómica de eventos de dominio (`AssistanceRequestedEvent`, `OperatorAssignedEvent`) en la base de datos relacional PostgreSQL de `fixgo-dispatch-service` antes de enviarlos a RabbitMQ.             |
| **CQRS**                       | Partial  | Reservado únicamente para lecturas geoespaciales intensivas en `fixgo-location-service` (donde las ubicaciones activas se almacenan y consultan en modelos de Redis Spatial separados del modelo de persistencia relacional). |
| **Event Sourcing**             | No       | Descartado en la fase actual por complejidad innecesaria. La auditoría de los tickets de asistencia se gestiona mediante tablas de histórico de estados y campos de auditoría.                                                |
| **BFF (Backend for Frontend)** | No       | Las aplicaciones móviles (Conductor y Mecánico/Grúa) y la aplicación web de Talleres comparten contratos unificados expuestos a través del API Gateway. Se evaluará en v2.0 si las vistas divergen significativamente.        |
